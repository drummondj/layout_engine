1. `Geometry::path_to_polygons` (real Boost.Geometry buffering, not cheap) was being recomputed from scratch for every routed Path on *every* Rasterize call - the pre-restart pipeline avoided exactly this by caching it once per Shape at shape-generation/Cold time (`RenderedShape::path_outlines`); the new pipeline's `Shape` (a `schema.py` type, reused directly rather than duplicated) has no field of its own to cache into, so a schema change was deliberately avoided in favor of a pipeline-local cache instead (`RasterizeStage::path_outline_cache_by_node_`, keyed per node/HierarchyId, holding the node's own current `data.shapes` handle to detect a real upstream recompute).
2. 1. **Follow-up, real reported bug**: the whole-string bitmap cache above has an unbounded-memory problem, reported directly by the user testing `aes_scaling_4x4.def` at `hierarchy_depth = 0` (placement-name labels only, one label per instance, no descent into any Abstract's own pin labels): "Everytime I zoom in memory usage exponentially increases until the process is killed." Per explicit direction, left the cross-node rotation/flip gap unfixed (a real architecture change - text as a separate overlay pass after compositing - not a quick patch) and removed `UprightTextCanvas` entirely, since its only remaining real job (correcting the ambient y-flip+scale *within* one node's own render pass, the CTM there never having a rotation component to discard in the first place) is exactly what Blend2D's own text drawing already does more directly: map the label's dbu-space origin through the canvas's current matrix once to a real device-pixel point, then draw under a plain translate-only matrix at that point. `rasterize_stage.hpp`'s own text loops (both the generic per-shape case and the placement-name case) now do the same thing directly, with no intercepting canvas class needed - `upright_text_canvas.hpp`/`.cpp` deleted, its `-fno-rtti` `set_source_files_properties` entry (needed only for that one file's `SkPaintFilterCanvas` subclass, this vendored Skia build having no `typeinfo for` symbol for it) removed from `CMakeLists.txt` along with it.

**A second, unrelated regression surfaced by the same investigation**: `default_typeface()` (Skia) loaded "DejaVu Sans Mono" instead of "DejaVu Sans" - a side effect of `DejaVuSansMono.ttf` (added for Blend2D, see the "unbounded memory growth" entry above) living in the same `LE_FONT_DIR` that function scans. `try_font_dir`'s own `createStyleSet(0)` logic assumes exactly one bundled family lives there; with two present, which one Skia picked was down to `SkFontMgr_Custom`'s own family enumeration order - filesystem-dependent, not alphabetical, and not something either font-loading function controls. Per direction ("use the same monospaced font for both"), fixed at the root rather than patched around: `DejaVuSans.ttf`/`DejaVuSans-Bold.ttf` deleted (already unreferenced by any code path), leaving `DejaVuSansMono.ttf` as `assets/fonts/`'s only font - `createStyleSet(0)`'s own "exactly one family" assumption is true again by construction, and both backends now render from the identical bundled family.

**A third, more consequential bug found while replacing `UprightTextCanvas`**: its own substitute matrix, `Scale(scale, scale)` where `scale = sqrt(|det(ctm)|)`, evaluates to exactly `options.scale` (the per-node canvas's own ambient dbu-to-pixel scale) - but the `pixel_size` used to construct each label's own `SkFont` already has that same `scale` baked into it (`text.size * scale * kLabelWidthRatio`, clamped to `[kMinLabelPixelSize, kMaxLabelPixelSize]`). `UprightTextCanvas` was reapplying it a second time, so a label's own real rendered size was `pixel_size * scale`, not `pixel_size` - quadratic in zoom, not linear, silently defeating the whole point of the `kMin`/`kMaxLabelPixelSize` clamp (which only ever bounded the *first* factor). At this session's own `compose_stage_test.cpp` fixture's `scale = 4`, a nominally-"12px" label was actually rendering around 48px. A related discrepancy affected placement-name padding specifically: `kPlacementLabelPaddingPx` was passed through `drawString`'s own `(x, y)` argument *before* interception, so it too was scaled by that same extra factor, and - the substitute matrix having no y-flip - ended up moving the label *down* (toward/past the box's own bottom edge), the opposite of the constant's own documented intent ("doesn't visually touch its... bottom edge", "stays a constant inset regardless of zoom").

Per direction, fixed rather than bug-for-bug replicated: the new device-space code renders each label at the literal `pixel_size` (matching Blend2D's own, already-shipped, already-correct convention) with `kPlacementLabelPaddingPx` applied once, directly in device-pixel space, in the actually-intended direction (right and up the screen from the box's own bottom-left device point). One existing test, `ComposeStageFixture.ComposesA90DegreeRotatedChildAtTheCorrectlyTransformedOffset`, broke as a direct result - not because the fix was wrong, but because that fixture's own placement coordinates ((20,20)/(30,30)) happen to put BLOCK's own always-drawn "leaf0" placement-name label directly on top of the one pixel the test samples to confirm the *terminal rect's* own rotation (both derived from the same coordinates, a coincidence of the fixture, not a real interaction) - the test was only ever passing because the old, oversized/mispositioned label happened to land somewhere else by the old bug's own accidental magnitude. Fixed by hiding the `PLACEMENT_NAME` purpose for this fixture (`options.purpose_visible[ViewLayerPurpose::PLACEMENT_NAME] = false`), scoping it to what it actually tests (geometry rotation, not label rendering, which no test in that file otherwise exercises) rather than re-deriving new pixel expectations by hand.

Re-verified the flip case visually after the fix (same three-placement N/FN/FS test): the unflipped label now renders at its correct, literal 12px size, comfortably within its own terminal box (previously oversized well beyond it); the flipped cases still mirror consistently, as expected given the cross-node gap is deliberately left unfixed.
