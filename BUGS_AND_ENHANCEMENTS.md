# BUGS

- [x] B1. The terminal/route fill pattern does not work at different zoom levels. Not sure how long it has been like this.
- [ ] B2. Crash (EXC_BAD_ACCESS / SIGBUS) opening a large real Layout view (reproduced with ispd19_test10's real DEF, full-screen viewport, via the Tracy profiling integration test - frontend/scripts/profile_tcl_script.sh). Faulting thread is a TBB worker thread inside `LayerVisibilityFilterStage::compute()` (backend/src/pipelines/stages/layer_visibility_filter_stage.hpp), reached via `HierarchyResolver::record_local_picture` -> `build_layout_picture_uncached` -> `render_layout_frame` -> `le_render_pixel_buffer` (backend/src/pipelines/hierarchy_resolver.hpp), while the calling raster thread is shown blocked inside `wait_for_all()` for that exact stage - consistent with a use-after-free on `record_local_picture`'s call-local `SynchronousStageRunner<LayerVisibilityFilterStage,...>` (a fresh instance per call, per that class's own documented correctness fix) if a TBB task tied to its graph outlives the call. Not reproduced by any existing unit test (all use small synthetic fixtures) - this was the first real large-scale/full-window exercise of HierarchyResolver's Layout-view path since the oneTBB migration (backend/ONETBB_INTEGRATION.md), so likely a pre-existing latent concurrency bug rather than a regression from any single recent change. Needs a proper isolated repro (ideally a stress-test fixture in backend_tests, not just the ispd19 DEF) before attempting a fix.
