# BUGS

- [x] B1. The terminal/route fill pattern does not work at different zoom levels. Not sure how long it has been like this.
- [x] B2. Crash (EXC_BAD_ACCESS / SIGBUS) opening a large real Layout view (reproduced with ispd19_test10's real DEF, full-screen viewport, via the Tracy profiling integration test - frontend/scripts/profile_tcl_script.sh). Faulting thread was a TBB worker thread inside `LayerVisibilityFilterStage::compute()`, reached via `HierarchyResolver::record_local_picture` -> `build_layout_picture_uncached` -> `render_layout_frame` -> `le_render_pixel_buffer`, while the calling raster thread was blocked inside `wait_for_all()` for that exact stage. Initially misdiagnosed as a pre-existing, unrelated latent bug; an A/B test against a pre-E2 worktree (identical script, identical scale) proved E2 was the actual trigger - E2 made TRACK_PREFERRED/TRACK_NON_PREFERRED/ROW/GCELLGRID hidden by default, which turned `LayerVisibilityFilterStage::compute()`'s erase-branch from a near no-op into real, heavy per-frame work on a real design - stretching that one TBB task's runtime enough to reliably expose a pre-existing, narrow TBB nested-flow-graph race in `HierarchyResolver`'s recursive Layout-view path (`record_local_picture` constructed a fresh `tbb::flow::graph`, via `SynchronousStageRunner`, on every recursive call, purely as a single-shot call adapter with no caching/async benefit ever used there). ThreadSanitizer could not be used to pin down the exact race directly - confirmed via a minimal, unrelated repro (a bare `tbb::flow::graph` + one node) that Homebrew's precompiled `libtbb.12.dylib` is incompatible with Xcode's bundled TSan on this macOS/Apple Silicon machine (crashes inside TSan's own runtime, `__tsan::SlotLock`, not in application code). Fixed by removing the hazard by construction instead: `filter_shapes_by_viewport`/`filter_shapes_by_layer_visibility` (`viewport_filter_stage.hpp`/`layer_visibility_filter_stage.hpp`) are now plain functions containing the same logic, called directly from `record_local_picture` with no `tbb::flow::graph` involved at all; `ViewportFilterStage`/`LayerVisibilityFilterStage` (used elsewhere via real persistent pipeline graphs, where `MemoizingStage` caching does matter) now just call these functions from their own `compute()`. Also fixed `LayerVisibilityFilterStage`'s own filter to build its result map directly from visible shapes instead of grouping everything first and erasing most of it back out. Verified: 629/629 backend tests pass, and two consecutive real runs of the exact previously-crashing `read_ispd19_test10.tcl` scenario now pass cleanly ("All tests passed!").
